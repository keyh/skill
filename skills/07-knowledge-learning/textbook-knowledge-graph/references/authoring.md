# 写法：节点、证据、检测问题、先修关系

## 一、节点：一个可教、可检测的想法

判断标准（三条都满足才算一个节点）：
1. 能用一两句话说清它是什么；
2. 能写出 2–4 条可观察的达标证据；
3. 一个教学片段（约 10–20 分钟）能讲完、一个问题能检测。

**该拆**：名称里有“与”“及”“和”并列两件可分开学的事（“诊断标准与分级”通常可以留在一起，“饮食与运动指导”通常该拆）；证据超过 4 条；一部分是概念、一部分是操作。

**该并**：多个项目里反复出现、内容实质相同的通用知识（照护原则、健康教育方法、风险评估思路、沟通技巧）。并成一个基础节点，放在第一次讲它的项目，`anchors` 记下所有出处；各病种里的具体应用若有特定内容（如“糖尿病老人的饮食控制”），保留为独立节点，并用 `hard` 或 `soft` 边连到基础节点。

**别凭空加**：节点要能对应稿件里的知识点或细目。确实缺一个必要的前置（例如书里没讲但后面反复用到的“生命体征正常值”），可以加，但 `notes` 写“稿件未单列，建议补充”，并保持 `status: "ai"`。

### 类型

| 类型 | 中文 | 判断 | 例子（护理 / 中医药类） |
|---|---|---|---|
| `CONCEPTUAL` | 概念 | 理解是什么、为什么 | 老年高血压的特点；气血津液的关系 |
| `PROCEDURAL` | 操作 | 按步骤做出来 | 测量血压；艾灸的操作流程 |
| `REPRESENTATIONAL` | 识读 | 读懂或画出某种表示 | 读懂血糖记录表；辨识舌象图；看懂经络循行图 |
| `LANGUAGE` | 术语 | 掌握专门用语和表达 | 常用医学术语；中医病证名称规范 |
| `META` | 素养 | 职业素养、伦理、自我监控 | 照护中的尊重与隐私保护；自我评估照护效果 |

拿不准时：要“做”的选操作，要“懂”的选概念。

### 描述与达标证据

- 描述写“讲什么 + 学完能怎样”，不要照抄标题，也不要写成目录。
- 证据以“能”开头，写**看得见的行为**和**判断标准**，避免“了解”“掌握”“熟悉”这类看不见的词。
  - 差：能了解老年高血压的特点。
  - 好：能说出老年高血压与中青年相比的 3 个特点，并各举一个照护上的影响。
- 证据要能对上任务评价表里的技能点；对上了就在 `standards` 里写 `skill:` 编号。

### 检测问题

- 一句话，教师可以直接问，AI 助手可以拿来“先反问”。
- 优先用情境：“张奶奶早上血压 168/96，她说没有不舒服，你怎么判断、下一步做什么？”
- 需要称呼学生时用占位符 `{{name}}`（如“{{name}}，张奶奶早上血压 168/96……”），由页面或 AI 助手替换；不写真实姓名，不写标准答案（答案要点可放 `notes`）。

## 二、先修关系

### 只连直接先修
问自己：“学 B 时，具体要**直接用到** A 的什么？”说得出来才连。若 A → B → C 都成立，就不要再连 A → C。`validate.py` 会把冗余边标出来。

### 硬还是软
- `hard`：不会 A，B 无法开始，或一定会学错。例如不会判断血压分级，就无法确定监测频率。
- `soft`：会 A 能让 B 学得更快、更好，但不是必需。例如了解老年人心理特点，有助于做好用药依从性沟通。
- 拿不准用 `soft`。硬边是学习路径和“缺什么”诊断的主干，宁缺毋滥。
- 分析时软边只看直接一层，不会被一路追溯；所以“A 有助于 B”就是软边，不必为了把 A 拉进学习路径而标成硬边。
- 全书试跑（《老年疾病照护》）的比例约为硬 3 : 软 7，大多数节点 1–3 条直接先修；硬边少于两成或多于一半时，回头抽查判断标准是否一致。

### 理由
一句话，指出具体用到什么：“制定饮食方案要先会计算每日能量需要量”。不要写“A 是 B 的基础”这种空话。

### 方向与顺序
- 边从“先学的”指向“后学的”。
- 先修一般在同一项目的前面任务，或更靠前的项目。若先修在更靠后的项目，`validate.py` 会提示：多半是方向反了；如果确实如此，说明教材编排有问题，在报告里提给编辑（例如“项目 3 用到了项目 9 才讲的知识，建议在项目 3 加提示”）。

### 每个节点连多少
大多数节点 1–3 条直接先修；起点知识可以没有先修。一个节点超过 4 条直接先修，通常说明它太大了，考虑拆分。

## 三、分批做整本书

一本 16 个项目、约 280 个知识点的书（《老年疾病照护》全书试跑：6 组并行，约 50 分钟，得到 307 个节点、558 条边）：
1. 分 5–6 组，每组 2–4 个项目，并行处理：整理节点、写字段、建项目内先修，以及**指向更靠前项目**的跨项目先修（直接用骨架 id，即使那个节点属于别的组）。每组只改自己负责的项目；合并或拆分时把旧 id 记进 `merged` 映射，合并时据此改写别组的引用。不能建指向更靠后项目的边，发现“先用后讲”就记下来。
2. 合并后做一轮**全书整理**：处理各组提出的跨项目重复（不合并节点，用软边连回第一次讲的地方，记进 `editorial.repeats`），处理“先用后讲”（记进 `editorial.forwardUse`），再跑 `validate.py --fix-redundant`。
3. 跑 `validate.py`，处理循环、冗余、顺序冲突。
4. 跑 `analyze.py --report`，看重点、难点是否合理；明显不合理的（例如一个冷门知识点中心度很高）回头查边。

## 四、审核

- 导出 `analyze.py --review 审核表.csv` 给编辑：每条边、每个节点一行，最后一列填“接受 / 修改 / 删除”。
- 按审核意见改 kg.json：接受的改 `status: "reviewed"`；删除的边改 `rejected`，不要直接删掉；作者确认后改 `confirmed`。
- 页面上，`ai` 状态的关系显示“AI 预生成 · 待审核”；对外统计数字（如“先修关系 n 条”）只计 `reviewed` 和 `confirmed`，或者写明包含待审核部分。

## 五、交付前检查
- [ ] `validate.py --book book.json` 无错误；警告已处理或在说明里解释
- [ ] 每个原知识点都有对应节点（覆盖率 100%），合并的节点 `anchors` 齐全
- [ ] 抽查 10 条硬边：理由具体、方向正确、确实是直接先修
- [ ] 重点 / 难点候选与教材的“重点难点”栏目基本一致，不一致的给出解释
- [ ] 审核表已导出，`status` 如实
